# AUDIT — Live `ready-set-dedicate` v5 vs. current demo state (Draft 66)

**Date:** 2026-08-14 · **Author:** Claude Code · **Mode:** read-only reconnaissance — no schema changes, no republish, no activity edits.

**Scope:** diff the published live intervention (version 5, published 2026-07-24, the 2026-07-22 assent-title republish) against the current demo/sandbox state of the platform, and produce the insertion plan for the 9 produced videos (+1 TBD) ahead of the 8/28 beta. Follow-up drafts execute; this document only maps the work.

**Method:** pulled the v5 `snapshot_json` (14 sections / 57 items) straight from `intervention_versions` via SQL; compared the working `sections`/`items` tables against the snapshot; read the delivery engine, all item renderers, all edge-function sources, and the locked sandbox survey components.

---

## 0. Baseline facts

- **The working (builder) tables are byte-identical to the published v5 snapshot.** A full outer join on `(section order_index, item order_index)` comparing `content_json` returned zero differences. Any republish starts from a known-clean working state — nothing half-edited is sitting in the builder.
- **Live delivery renders the frozen snapshot** (`get-version-snapshot`), but `custom_activity` items resolve their component **at runtime** from `ACTIVITY_REGISTRY` (`src/lib/activityRegistry.js`). Activity-level improvements ship to live participants **without a republish**.
- **Resume is section-granular** (`sessions.current_section`); item position within a section is not persisted. Responses persist per item via `save-response` (upsert on `(session_id, item_id)`), restored at bootstrap by `get-session-responses` keyed by `token_key` and by item id.
- **There is no session-level metadata write path from the client.** `update-session-progress` (v2) whitelists `current_section` / `status` only. The token/pull-forward system (`{{response.<token_key>.<path>}}`, resolved client-side against saved responses) is the only session-shared state — this matters for Draft 67.

### A.4 Video item type (draft question B)

`VideoPlayer.jsx` is **Vimeo-only**: config is `{ vimeo_url, title, context_before/after, show_controls, autoplay, required_completion, completion_threshold }`, embeds `player.vimeo.com`, tracks progress via Vimeo postMessage events, and gates Continue at `completion_threshold` (default 0.85) when `required_completion: true`. **All 9 produced videos are YouTube.** The item type needs a YouTube mode before any video authoring can happen — this is Draft 67 Part C's `variants` extension plus a plain `youtube_id` single-source field (Draft 67 ships both). Note: YouTube's iframe cannot report progress without the IFrame API, so completion-gating parity for YouTube is a separate decision (see open questions).
